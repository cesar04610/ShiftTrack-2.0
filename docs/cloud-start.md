# Inicio de este entorno de desarrollo

Trabaja en la carpeta del repositorio ya clonada; cada tarea cloud está aislada y no requiere worktrees adicionales. Lee `README.md` y `docs/estado.md`. Un entorno local validado no equivale a un despliegue Railway operativo ni a un piloto aceptado.

Archivos y dependencias se conservan; PostgreSQL y los servidores deben reiniciarse cuando el entorno se restaura. No asumir que procesos ni conexiones sobreviven. No sobrescribir `.env`. Los datos de ejemplo (seed) solo se cargan en la base local de este entorno, nunca en Railway ni en otra base remota. Firebase y Java ya no son necesarios.

1. Si faltan dependencias o PostgreSQL, ejecuta `bash scripts/cloud-install.sh`. Conserva `.env`, usa `npm ci`, levanta PostgreSQL local en Docker, migra, carga el seed local idempotente y compila. Si el contenedor ya existe, usa `docker start shifttrack-postgres` y comprueba `docker exec shifttrack-postgres pg_isready -U shifttrack -d shifttrack`. Sin Docker, usa un PostgreSQL 17 local con el usuario, la contraseña y la base de `.env.example`.
2. Las nuevas migraciones se aplican con `npm run db:migrate && npm run db:seed`, solo en la base local. La API usa `shifttrack_app`, sin propiedad de tablas ni bypass RLS. El seed rechaza bases remotas y producción.
3. Inicia `npm run dev` en un proceso mantenido por la herramienta de terminal. API en 8080, Vite en 5173. Comprueba `curl --fail http://127.0.0.1:8080/api/v1/health`; un puerto abierto no prueba funcionamiento.
4. Para la PWA, ejecuta `npm run build:local` y luego `npx vite preview --config apps/web/vite.config.ts --port 5174` en otro proceso. `build` y `build:local` generan la misma interfaz; README, los helpers y CI usan `build:local`. No enviar enlaces localhost al usuario.
5. Verifica `npm test`, `bash scripts/ci-e2e.sh` (inicia API y preview solo durante la prueba), `npm run worker:tick` y `npm audit --omit=dev`. `npm test` ejecuta los archivos de prueba uno tras otro sobre PostgreSQL real; para resultados reproducibles, usa una base local recién migrada. No iniciar el helper E2E si ya usas esos mismos puertos. Usa Chromium del sistema o `CHROMIUM_PATH`.

Las cuentas públicas de ejemplo están en README y son solo locales. Las concesiones offline nuevas no vencen por tiempo; las sesiones online vencen a las nueve horas. No borrar pendientes ni restaurar saldos arbitrarios al ver un conflicto. No regenerar datos de ejemplo como sustituto de un respaldo.

Para Railway se usa un token de proyecto únicamente en HTTPS a `https://backboard.railway.com/graphql/v2`, cabecera `Project-Access-Token`. Puede guardarse en los ajustes seguros del entorno de desarrollo (por ejemplo, como `RAILWAY_PROJECT_TOKEN`) o inyectarlo automáticamente el proxy del entorno; en ese caso no se necesita la variable. Nunca imprimir su valor ni volcar variables o registros sensibles. El token de proyecto no concede permisos de facturación de la cuenta. Consultar primero el estado remoto y conservar el presupuesto del usuario. No confundir el commit en GitHub, una compilación y un despliegue saludable.

Si el constructor Docker no resuelve el proxy de este sandbox, usa la IP resuelta con `--add-host`, `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`. Para la CA pública de confianza del sandbox, exporta `NPM_CA_BASE64` con `base64 -w0 "$NODE_EXTRA_CA_CERTS"` y pasa `--build-arg NPM_CA_BASE64`; este argumento acepta únicamente el certificado público, nunca credenciales. No desactivar TLS ni guardar valores de credenciales/proxy en el repo. Fuera del sandbox la CA opcional suele ser innecesaria. Railway no admite el montaje BuildKit de secretos usado en la receta anterior.
